# Project declared Kafka retention into materialized views

## Status

Accepted; implementation is tracked by [PRD #400](https://github.com/bmvantunes/effect-view-server/issues/400) and child issues [#401](https://github.com/bmvantunes/effect-view-server/issues/401) and [#402](https://github.com/bmvantunes/effect-view-server/issues/402).

Every first-party Kafka Source Definition declares both its semantic cleanup policy and its View Server retention policy. The cleanup declaration is `delete`, `compact`, or `compact-and-delete`; the retention declaration is `match-kafka-retention` or an Effect `Duration.Input`. Compaction-capable sources derive `localRowKey` without the decoded value so tombstones remain identifiable, while delete-only sources may also use the decoded value and reject null-valued records instead of treating them as tombstones. Both declarations are mandatory because cleanup changes the public identity callback and retention changes row lifetime.

The aggregate Kafka Node Layer batches effective topic-configuration discovery per Region through `@platformatic/kafka` Admin before providing the Kafka Source Adapter Runtime Service. It normalizes `cleanup.policy` as an unordered whitespace-insensitive set, requires exact agreement with the declaration, and resolves `match-kafka-retention` from `retention.ms`. Failure is a typed Layer acquisition error and prevents the complete View Server Runtime Effect from starting. This deliberately creates a narrow exception to ordinary Source Supervision: running without a verified broker contract could silently corrupt the materialized view, and a health hook cannot make an invalid runtime safe.

Kafka Retention Projection uses the Kafka record timestamp and Region-resolved duration. A logical Materialized Topic lifetime owns a lightweight expiry index, keyed serialization, and one coarse Effect Clock sweep across Source Attempt retries. Each delivery acquires its canonical-ID permit as a scoped idempotent lease registered with the Source Attempt Scope before emission. Runtime Core applies the singleton Topic Row mutation and a closed nominal Source Application Transition in one serialized uninterruptible critical section. The transition comes only from the SDK-owned Source Application State Module; it contains no callback, Effect, requirement, Promise, I/O, or suspension. On successful mutation it replaces an Upsert deadline or removes a tombstone deadline and releases the lease; failed mutation leaves the prior generation unchanged, and attempt closure is the fallback before transition. External settlement happens afterward and cannot create a row/index gap. Transition-bearing multi-mutation deliveries are rejected because ordinary delivery application is not transactional.

A sweep uses `acquireRelease` for the same lease while rechecking generation. The Source Maintenance Interface applies the single ordinary Delete and a closed matching-generation removal transition in the same serialized uninterruptible critical section. A stale generation changes nothing, and a failed Delete leaves the row and generation indexed for later retry and backlog tracking. An internal transition-executor defect is fatal to the complete View Server Runtime Effect: external settlement/commit is suppressed, logical-lifetime closure releases the lease, and uncommitted Kafka replay reconstructs state. Non-completion is excluded by the closed operation. Because both row and index are in-memory, process death removes both and replay rebuilds both. Already-expired records never materialize and invalid items never refresh retention. The aggregate Kafka Node Layer supplies a positive finite sweep interval, defaulting to 15 minutes.

The Topic-Bound Source Toolkit gains one deep transport-neutral Source Maintenance Interface. It applies a nominal Topic-bound mutation through the ordinary Column Live View Engine mutation and Delta path, returns the complete application Exit to adapter-owned maintenance, and never routes failure into Source Supervision. It also reports active/recovered Adapter Maintenance Failure markers without Runtime Core inspecting Kafka metrics. Runtime Core keeps a logical-lifetime degradation ledger through every supervision phase: settled item rejection remains sticky, maintenance degradation clears when its failed-work backlog clears, and operational `Starting`, retry, exhaustion, and stopping statuses retain precedence. A later readiness transition selects `Degraded` when the ledger remains non-empty, while clearing the last maintenance reason during readiness returns to `Ready`. Exact safe Kafka failure details remain in Kafka Source Adapter Metrics. A failed expiration therefore remains retryable and globally visible without stopping ingestion, exposing Runtime Client, or leaking a Kafka branch into Runtime Core.

`match-kafka-retention` intentionally means configured time-based retention rather than an exact mirror of the physical Kafka log. Kafka removes segments rather than individual records, may remove them later than `retention.ms`, and may remove them for `retention.bytes`; View Server does not inspect broker segment state or emulate size-based retention. Compact-only sources and `retention.ms = -1` retain forever. A matched zero still uses the universal `record timestamp + duration` deadline, so it is immediately due only when the record timestamp is not later than the sweep's Effect Clock time; a future-dated record becomes due at its own timestamp. Explicit positive durations may be shorter or longer than Kafka retention, and Effect infinity explicitly retains forever; explicit zero and negative durations are invalid.
