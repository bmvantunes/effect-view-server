# Project declared Kafka retention into materialized views

## Status

Accepted; implementation is tracked by [PRD #400](https://github.com/bmvantunes/effect-view-server/issues/400) and child issues [#401](https://github.com/bmvantunes/effect-view-server/issues/401) and [#402](https://github.com/bmvantunes/effect-view-server/issues/402). For the target behavior, this decision supersedes ADR 0007's rejection-only `Degraded` payload with the transport-neutral non-empty degradation-reason set defined here. It also supersedes ADR 0009's one-shape Kafka `localRowKey` rule: compaction-capable identity is restricted to decoded key and Region, while delete-only identity may additionally use the decoded non-null value.

Every first-party Kafka Source Definition declares both its semantic cleanup policy and its View Server retention policy. The cleanup declaration is `delete`, `compact`, or `compact-and-delete`; the retention declaration is `match-kafka-retention` or an Effect `Duration.Input`. Compaction-capable sources derive `localRowKey` from decoded key and Region only, excluding per-record offset, timestamp, headers, and partition so tombstones remain identically addressable. Delete-only sources may additionally use the decoded non-null value and reject null-valued records instead of treating them as tombstones. Both declarations are mandatory because cleanup changes the public identity callback and retention changes row lifetime.

The aggregate Kafka Node Layer batches effective topic-configuration discovery per Region through `@platformatic/kafka` Admin before providing the Kafka Source Adapter Runtime Service. It normalizes `cleanup.policy` as an unordered whitespace-insensitive set, requires exact agreement with the declaration, and resolves `match-kafka-retention` from `retention.ms`. Failure is a typed Layer acquisition error and prevents the complete View Server Runtime Effect from starting. This deliberately creates a narrow exception to ordinary Source Supervision: running without a verified broker contract could silently corrupt the materialized view, and a health hook cannot make an invalid runtime safe. Validation is a point-in-time startup snapshot. V1 supports broker-policy changes only through coordinated stop, broker change, and restart of every affected instance; it deliberately does not poll, and mutation behind a running instance is outside the correctness contract.

Kafka Retention Projection uses the Kafka record timestamp and Region-resolved duration. A logical Materialized Topic lifetime owns a lightweight expiry index, keyed serialization, and one coarse Effect Clock sweep across Source Attempt retries. One Source Attempt Scope finalizer owns a live-lease registry. `Effect.uninterruptibleMask` makes permit acquisition and insertion of its idempotent lease into that registry one interruption-safe ownership transfer, releasing on registration failure before restoring interruption. Ordinary release removes the registry entry, bounding retained finalizer state by concurrent live leases. Runtime Core applies the singleton Topic Row mutation and a closed nominal Source Application Transition in one serialized uninterruptible critical section. The transition comes only from the SDK-owned Source Application State Module; it contains no callback, Effect, requirement, Promise, I/O, or suspension. On successful mutation it replaces an Upsert deadline or removes a Delete deadline and releases the lease; failed mutation leaves the prior generation unchanged, and the attempt registry is the fallback before transition. External settlement receives every complete application Exit exactly once afterward and cannot create a row/index gap. Transition-bearing multi-mutation deliveries are rejected because ordinary delivery application is not transactional.

The sweep launches new work only while the source is `Ready` or `Degraded`, preserving retained rows during retry and exhaustion. Each due item uses `Effect.acquireUseRelease`, or an equivalent fresh child `Effect.scoped` acquisition, for the same lease while rechecking generation; no permit is registered in the logical-lifetime sweep Scope. The SDK-owned Source Application State Module issues a closed Source Maintenance Operation bound to the exact keyed Delete and matching-generation removal transition. The Source Maintenance Interface accepts only that sealed operation, never an arbitrary Source Mutation, and applies it in the same serialized uninterruptible critical section. A stale generation changes nothing, and a failed Delete leaves the row and generation indexed for later retry.

A delivery Source Application Transition executor defect becomes that delivery's defective application Exit. Runtime Core passes it to Source Settlement exactly once; Kafka settlement does not commit a non-success Exit. A Source Maintenance Operation executor defect instead becomes the defective maintenance application Exit and invokes no Source Settlement. Both invariant breaches fail the complete runtime and close the logical lifetime; the maintenance `acquireUseRelease` or child Scope releases its lease. Safe reconstruction requires an authoritative replay position or durable checkpoint. Kafka v1 provides no checkpoint, so `latest`, `committed`, and bounded start positions do not guarantee automatic recovery of prior rows; recovery tests use an authoritative start. Non-completion is excluded by the closed operations.

An already-expired non-null authoritative record never produces a transient Upsert. Because Kafka timestamps need not be monotonic, it instead emits the same singleton keyed Delete and closed transition, removing a row produced by an earlier offset if present. Tombstones always take the keyed Delete path, and invalid items never refresh retention. The aggregate Kafka Node Layer supplies a positive finite sweep interval, defaulting to 15 minutes.

The Topic-Bound Source Toolkit gains one deep transport-neutral Source Maintenance Interface. It accepts only SDK-issued closed Source Maintenance Operations, applies them through the ordinary Column Live View Engine mutation and Delta path, returns the complete application Exit to adapter-owned maintenance, and never routes failure into Source Supervision. It also reports active/recovered Adapter Maintenance Failure markers without Runtime Core inspecting Kafka metrics. Runtime Core keeps a logical-lifetime degradation ledger through every supervision phase: settled item rejection remains sticky, while maintenance failed work is a set keyed by canonical ID plus generation. Repeated failures of one item increment retry metrics without increasing backlog cardinality; success or cancellation removes that exact item, and the marker clears when the set is empty. Operational `Starting`, retry, exhaustion, and stopping statuses and their derived Topic/aggregate health retain precedence. A later readiness transition selects `Degraded` when the ledger remains non-empty, while clearing the last maintenance reason during readiness returns to `Ready`. Exact safe Kafka failure details remain in Kafka Source Adapter Metrics. A failed expiration therefore remains retryable and globally visible during active operation without stopping ingestion, exposing Runtime Client, or leaking a Kafka branch into Runtime Core.

`match-kafka-retention` intentionally means configured time-based retention rather than an exact mirror of the physical Kafka log. Kafka removes segments rather than individual records, may remove them later than `retention.ms`, and may remove them for `retention.bytes`; View Server does not inspect broker segment state or emulate size-based retention. Compact-only sources and `retention.ms = -1` retain forever. A matched zero still uses the universal `record timestamp + duration` deadline, so it is immediately due only when the record timestamp is not later than the sweep's Effect Clock time; a future-dated record becomes due at its own timestamp. Explicit positive durations may be shorter or longer than Kafka retention, and Effect infinity explicitly retains forever; explicit zero and negative durations are invalid.
