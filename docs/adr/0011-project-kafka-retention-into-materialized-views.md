# Project declared Kafka retention into materialized views

## Status

Accepted; implementation is tracked by [PRD #400](https://github.com/bmvantunes/effect-view-server/issues/400) and child issues [#401](https://github.com/bmvantunes/effect-view-server/issues/401) and [#402](https://github.com/bmvantunes/effect-view-server/issues/402). For the target behavior, this decision supersedes ADR 0007's rejection-only `Degraded` payload and its Kafka tombstone Local Row Key example, using the exact transport-neutral canonical non-empty degradation-reason tuple and policy-specific Kafka identities defined in CONTEXT.md. It also supersedes ADR 0007's universal uninterruptible Source Settlement rule: callback application remains exactly once through a bounded masked handoff, while only the returned Effect is evaluated through the outer delivery mask's captured restore, owned, and interrupted by the Source Attempt Scope; the transition-defect path performs the supervised-child handoff below and never awaits settlement completion before root-fatal propagation. A synchronous callback throw becomes redacted typed `InvalidSourceSettlement` under Source Supervision only when ordinary termination wins the attempt's atomic cancellation arbitration before supervision handoff. A cancellation request made after the operation `Exit` was captured but before that handoff still wins and leaves the throw as secondary diagnostics only; during transition-defect handling, it is secondary to the original fatal defect. This decision supersedes three ADR 0009 Kafka contracts: `localRowKey` becomes delete-only; compaction-capable key codecs receive only serialized key bytes rather than Region or record metadata; and canonical Kafka identity/helpers use policy-specific partition-qualified IDs rather than `region:localRowKey`. Delete-only IDs are `region:partition:localRowKey`; compaction-capable IDs are exclusively `region:partition:k<unpadded-base64url(serializedKeyBytes)>`, preserving Kafka's exact byte equality in both directions without an application suffix. It also supersedes ADR 0010's Kafka-specific composition rule with those policy-qualified identities; ADR 0010's universal required `id: ViewServerId` contract remains unchanged. Delete-only callbacks receive decoded key, decoded non-null value, and Region; compaction-capable definitions expose no identity callback, and the adapter owns partition plus serialized-key identity.

Every first-party Kafka Source Definition declares both its semantic cleanup policy and its View Server retention policy. The cleanup declaration is `delete`, `compact`, or `compact-and-delete`; the retention declaration is `match-kafka-retention` or an Effect `Duration.Input`. Compaction-capable sources use a metadata-free key codec that decodes only non-null serialized key bytes and expose no `localRowKey`. Before decoding, the Kafka server Adapter captures the exact bytes and derives the complete canonical ID from Region, partition, and SDK-owned reversible injective unpadded-base64url Serialized Kafka Key Identity. Source Definition codecs and Mapping callbacks cannot observe this identity before Adapter injection, and application code cannot supply, normalize, hash, suffix, or override its derivation. Within one Region and partition, byte-equal keys always address one row and byte-distinct keys always address distinct rows, independent of decoded-key equality or application behavior; Region and partition remain deliberate identity namespaces. Policy-specific browser-safe helpers accept `Uint8Array`, use no Node dependencies, and disclose that the resulting public compact IDs reversibly encode key bytes; Runtime Core receives only the nominal final ID. Delete-only sources require `localRowKey` over decoded key, decoded non-null value, and Region, and reject null values instead of treating them as tombstones. Both declarations are mandatory because cleanup changes the public identity API and canonical ID, while retention changes row lifetime.

The aggregate Kafka Node Layer batches effective topic-configuration discovery per Region through `@platformatic/kafka` Admin before providing the Kafka Source Adapter Runtime Service. It normalizes `cleanup.policy` as an unordered whitespace-insensitive set, requires exact agreement with the declaration, and resolves `match-kafka-retention` from `retention.ms`. Failure is a typed Layer acquisition error and prevents the complete View Server Runtime Effect from starting. This deliberately creates a narrow exception to ordinary Source Supervision: running without a verified broker contract could silently corrupt the materialized view, and a health hook cannot make an invalid runtime safe. Validation is a point-in-time startup snapshot. V1 supports broker-policy changes only through coordinated stop, broker change, and restart of every affected instance; it deliberately does not poll, and mutation behind a running instance is outside the correctness contract.

Kafka Retention Projection uses the Kafka record timestamp and Region-resolved duration. Kafka timestamps and deadlines are Unix-epoch nanoseconds: validated Kafka milliseconds and non-negative safe-integer Effect `Clock.currentTimeMillis` are converted separately with `BigInt(milliseconds) * 1_000_000n`, then duration addition and comparison stay in `bigint`. Monotonic `Clock.monotonicTimeNanos` is never compared with a Kafka timestamp; Effect sleep/TestClock owns sweep cadence, so wall-clock jumps affect eligibility but not cadence. A logical Materialized Topic lifetime owns a lightweight expiry index, a lifetime-monotonic `bigint` generation sequence, keyed serialization, and one coarse Effect Clock sweep across Source Attempt retries. Every finite deadline receives a fresh generation token that is never reused within that lifetime, including after keyed Delete and same-ID reinsertion; only lifetime destruction may reset the sequence. Each Kafka Region first flattens or `Stream.rechunk(1)`s every upstream transport batch into singleton record chunks before the first mapping stage that can acquire a canonical-ID permit. For one singleton, all rejection-prone decoding, delete-only Local Row Key, Mapping, canonical-ID validation, and complete Topic Row validation finishes before permit acquisition; a Source Item Rejection therefore settles with no lease. Only a fully validated Upsert or keyed Delete may acquire and retain its lease until downstream application. This prevents both same-ID chunk self-deadlock and rejection-path lease stranding. One Source Attempt Scope finalizer owns a live-lease registry. Before any Upsert or keyed Delete delivery—including compaction-capable tombstones and already-expired non-null authoritative records—permit contention waits interruptibly. Inside `Effect.uninterruptibleMask`, only `acquirePermit(id)` is restored or made explicitly interruptible; after it succeeds, bounded insertion of its idempotent lease into the registry and ownership transfer remain masked. An interrupted wait owns no permit, and registration failure or defect releases the lease before leaving the mask. Ordinary release removes the registry entry, bounding retained finalizer state by concurrent live leases. Runtime Core requires every transition-bearing retention delivery to contain exactly one mutation, rejecting multi-mutation shapes in public types and defensive runtime validation. It applies that singleton Topic Row mutation and a closed nominal Source Application Transition in one serialized uninterruptible critical section. The transition comes only from the SDK-owned Source Application State Module; it contains no callback, Effect, requirement, Promise, I/O, or suspension. On successful mutation it allocates and replaces an Upsert deadline generation or removes every keyed Delete deadline without making its generation reusable, including compaction-capable tombstones and already-expired non-null records, and releases the lease; failed mutation leaves the prior generation unchanged, and the attempt registry is the fallback before transition. External settlement receives every complete application Exit exactly once afterward and cannot create a row/index gap.

The sweep launches new work only while the source is `Ready` or `Degraded`, preserving retained rows during retry and exhaustion. Each due item uses `Effect.acquireUseRelease(Effect.interruptible(acquirePermit(id)), use, releaseLease)` or an equivalent fresh child-Scope bracket with an explicitly interruptible blocking wait and masked finalizer transfer/release; bare `Effect.acquireUseRelease(acquirePermit(id), ...)` is non-conformant because Effect masks acquisition. Scope closure while waiting cancels the waiter without waiting for the holder and performs no mutation or failed-work transition. After acquisition it enters the Source Maintenance Interface. That Interface and Source Supervision share one Runtime Core-owned Source Lifecycle Gate. While holding the lease and Gate, the Interface atomically rechecks the never-reused generation, admits only `Ready` or `Degraded`, and linearizes the closed mutation, adapter-state, failed-work, and transport-neutral degradation-ledger outcome before returning the application Exit. A stale candidate performs no row mutation, preserves the current newer generation, and removes only the obsolete due entry and its exact failed-work identity. In particular, a candidate captured before Delete and same-ID reinsertion cannot match the reinserted row's fresh token. A deterministic race fixture pauses that candidate before permit acquisition, completes Delete and reinsertion with a new generation, resumes the candidate, and proves zero mutation of the new row/deadline plus removal of only obsolete candidate/backlog state. An inactive status performs no mutation and retains the same due entry and failed-work identity for the next active sweep. No permit is registered in the logical-lifetime sweep Scope. The Source Maintenance Operation is sealed and binds all outcome transitions; there is no separate report/recover callback and no arbitrary Source Mutation. A failed Delete atomically leaves the row/generation indexed and activates failed work. The logical Materialized Topic Scope owns the sweep fiber and its supervisor joins it. Only Scope-close interruption is ordinary; any other failure or premature completion completes a Runtime Core fatal signal that is structurally raced by the root View Server Runtime Effect, closing the listener and every logical lifetime rather than merely failing a child fiber.

A delivery Source Application Transition executor defect becomes that delivery's defective application Exit inside the one outer delivery `Effect.uninterruptibleMask((outerRestore) => ...)`. Runtime Core registers an attempt-owned supervised settlement child while still masked; the child's bounded masked prefix applies the Source Settlement callback to the Exit exactly once to obtain its Effect while capturing synchronous throw as secondary failure, records the SDK-owned invocation marker, and signals the handoff latch. If an Effect was returned, the child then evaluates only `outerRestore(returnedSettlementEffect)`. It never enters a nested mask and uses that nested mask's restore, which would restore only to the already-uninterruptible status. Runtime Core awaits only the latch and then completes the shared fatal signal. Source Settlement callback application is synchronous construction only and must promptly return its Effect without I/O, blocking, timers, Promise work, Effect execution, or unbounded computation. Exactly-once means callback application, not settlement completion or the first adapter-effect instruction. Fatal propagation never awaits settlement completion, while root shutdown cannot reduce callback invocation to zero for a conformant callback. Settlement failure or callback throw is secondary diagnostics and cannot mask the original defect, and Kafka does not commit this fatal non-success application Exit. Ordinary item-local Source Item Rejections are not fatal application Exits and use ADR 0007's same interruptible outer-restore workflow: rejection recording produces the complete `Exit`, Rejection Settlement callback application occurs exactly once in the bounded masked prefix, and only the returned Effect runs under the captured outer restore in the Source Attempt Scope. Kafka commits the rejected offset only after successful recording and settlement. A synchronous callback throw becomes exact redacted `InvalidSourceSettlement`, and a typed returned failure enters ordinary Source Supervision, only when ordinary termination wins the attempt's atomic cancellation arbitration before supervision handoff. A cancellation request made after the recording `Exit` was captured but before that handoff still wins: callback application and failed-settlement accounting occur once, but the throw is secondary diagnostics with no Source Termination, callback-throw-induced Source Supervision health transition, Schedule advancement, retry/reacquisition, or commit. First-party and conformance fixtures gate delivery and rejection returned Effects and prove callback application, marker/latch, and fatal-signal completion occur before the relevant gate opens; an interruptible `Effect.never` must be interrupted and joined on Scope closure. Rejection fixtures also prove callback count one, ordinary-termination synchronous throw and typed failure, cancellation requested after Exit capture but before callback application, shutdown without retry or reacquisition, and no commit. Blocking callback application and an interruption-masking returned Effect are tested separately as non-conformant, with no claim that Runtime Core can forcibly terminate arbitrary hostile user code. On an ordinary delivery for which cancellation has not won, a synchronous callback throw becomes exact redacted `InvalidSourceSettlement`, increments failed settlement once, commits nothing, and enters ordinary Source Supervision without completing the fatal signal. A Source Maintenance Operation executor defect becomes the defective maintenance application Exit, invokes no Source Settlement, and completes the same fatal signal. The root Runtime Effect races that signal, so both invariant breaches close the complete runtime and all logical lifetimes; the maintenance bracket releases its lease. Safe reconstruction requires an authoritative replay position or durable checkpoint. Kafka v1 provides no checkpoint, so `latest`, `committed`, and bounded start positions do not guarantee automatic recovery of prior rows; recovery tests use an authoritative start. Non-completion is excluded by the closed state operations.

Cancellation assertions distinguish callback-induced supervision state from state already produced by the operation. Delivery cancellation produces no callback-throw-induced supervision health transition. When rejection recording completed before cancellation won arbitration, its `rejectedItemCount`, sticky rejection ledger, `Degraded` publication, and exact metrics remain subject to operational shutdown-status precedence; the callback throw adds no Source Termination, supervision health transition, Schedule step, retry/reacquisition, commit, or Runtime Fatal Signal.

An already-expired non-null authoritative record never produces a transient Upsert. Because Kafka timestamps need not be monotonic, it instead emits the same singleton keyed Delete and closed transition, removing a row produced by an earlier offset if present. Compaction-capable tombstones always take the keyed Delete path; delete-only null records are settled Source Item Rejections, and invalid items never refresh retention. The aggregate Kafka Node Layer supplies a positive finite sweep interval, defaulting to 15 minutes.

The Topic-Bound Source Toolkit gains one deep transport-neutral Source Maintenance Interface backed, when declared, by one SDK-owned Source Application State Module per logical source lifetime. A `SourceAdapterServer.make(...)` lifecycle implementation declares zero or one nominal descriptor: stateless lifecycles declare none, while every retention-capable Kafka materialized lifecycle declares exactly one. Runtime Core validates descriptor shape, nominal linkage, cardinality, Topic binding, initial state, and required capability during composition before acquiring any listener, Source Attempt, consumer, or sweep; invalid static registration is a typed Runtime Composition Failure. It instantiates the declared Module once per logical source lifetime; the same instance survives retries and closes with the lifetime. An impossible duplicate, late, or logical-lifetime-mismatched registration after composition completes the Runtime Fatal Signal and never enters Source Supervision or health-only degradation. Its descriptor contains validated immutable initial state and one total synchronous prompt-return reducer for a closed nominal command algebra. That reducer is the explicit Adapter seam, performs no Effect, Promise, I/O, timer, or blocking work, and is never embedded in an issued operation. The SDK implementation owns synchronization; adapters receive nominal transition/maintenance constructors, an infallible local metrics snapshot read, and one deep `runDueSweep(epochNowNanos)` operation only for maintenance-capable registrations. `runDueSweep` privately enumerates the due index, rechecks each generation, owns the interruptible canonical-ID permit bracket and closed Source Maintenance Operation execution, and returns only an aggregate outcome. It exposes no due collection, cursor, claim token, index, lock, work identity, or arbitrary mutation; Runtime Core receives only private application operations and never sees adapter state or interprets Kafka metrics. Public `.test-d.ts` coverage proves exact initial-state, command, reducer-result, metrics-snapshot, and maintenance-capability inference without `as const`, optional stateless registration, mandatory single Kafka-retention registration, and rejection of missing, duplicate, wrong-lifecycle, cross-Topic, structural, async, Promise-returning, Effect-returning, fallible, and wrong-result descriptors or reducers, plus rejection of `runDueSweep` access from stateless registrations or any public due-candidate/index API. The Source Maintenance Interface accepts only those SDK-issued closed Source Maintenance Operations, applies them through the ordinary Column Live View Engine mutation and Delta path, returns the complete application Exit to module-owned maintenance, and never routes an expected failure into Source Settlement or Source Supervision. Each operation binds its stable work identity plus closed success/failure state and degradation transitions; Runtime Core executes mutation outcome, failed-work state, exact adapter metrics state, and the transport-neutral marker as one interruption-safe outcome under the Source Lifecycle Gate rather than accepting a later adapter report/recover call. Runtime tests prove due enumeration remains inside this Module and no private index shape crosses either face. Runtime Core keeps that logical-lifetime degradation ledger through every supervision phase: settled item rejection remains sticky, while maintenance failed work is a set keyed by canonical ID plus generation. Repeated failures of one item increment retry metrics without increasing backlog cardinality. A successful retry removes the exact identity with its row/index generation; a newer successful delivery atomically replaces or removes the generation and cancels its now-stale identity. Interruption, retry suspension, and exhaustion retain the identity while its due generation remains indexed; explicit stale-generation observation may cancel it. The marker clears when the set is empty. Operational `Starting`, retry, exhaustion, and stopping statuses and their derived Topic/aggregate health retain precedence. Every successful Source Attempt acquisition establishes operational readiness, selecting visible `Ready` when the ledger is empty or `Degraded` when reasons remain. Maintenance failure and recovery publish their Source Status plus derived Topic/aggregate health transitions immediately with the latest cached metrics. Kafka Source Adapter Metrics retain the latest exact safe maintenance failure and cumulative failure state for the logical lifetime. Recovery clears active backlog and health state but not those retained diagnostics; only metric-only detail changes coalesce into the next ordinary one-second sample, so sub-cadence failure and recovery appears in at least that next bounded metrics publication without an immediate metrics refresh. A failed expiration therefore remains retryable and globally visible during active operation without stopping ingestion, exposing Runtime Client, or leaking a Kafka branch into Runtime Core.

`match-kafka-retention` intentionally means configured time-based retention rather than an exact mirror of the physical Kafka log. Kafka removes segments rather than individual records, may remove them later than `retention.ms`, and may remove them for `retention.bytes`; View Server does not inspect broker segment state or emulate size-based retention. Compact-only sources and `retention.ms = -1` retain forever. A matched zero still uses the universal `record timestamp + duration` deadline, so it is immediately due only when the record timestamp is not later than wall epoch time from Effect `Clock.currentTimeMillis`; a future-dated record becomes due at its own timestamp. Explicit positive durations may be shorter or longer than Kafka retention, and Effect infinity explicitly retains forever; explicit zero and negative durations are invalid.
