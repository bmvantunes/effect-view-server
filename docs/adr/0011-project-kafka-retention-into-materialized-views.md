# Project declared Kafka retention into materialized views

## Status

Accepted; implementation is tracked by [PRD #400](https://github.com/bmvantunes/effect-view-server/issues/400) and child issues [#401](https://github.com/bmvantunes/effect-view-server/issues/401) and [#402](https://github.com/bmvantunes/effect-view-server/issues/402). For the target behavior, this decision supersedes ADR 0007's rejection-only `Degraded` payload with the transport-neutral non-empty degradation-reason set defined here. It supersedes three ADR 0009 Kafka contracts: the one-shape `localRowKey` rule becomes cleanup-policy-specific; compaction-capable key codecs receive only serialized key bytes rather than Region or record metadata; and canonical Kafka identity/helpers use `region:partition:localRowKey` with two separator boundaries rather than `region:localRowKey` with one. Compaction-capable callbacks remain restricted to decoded key and Region, delete-only callbacks may additionally use the decoded non-null value, and the adapter owns the partition component.

Every first-party Kafka Source Definition declares both its semantic cleanup policy and its View Server retention policy. The cleanup declaration is `delete`, `compact`, or `compact-and-delete`; the retention declaration is `match-kafka-retention` or an Effect `Duration.Input`. Compaction-capable sources use a metadata-free key codec that decodes only non-null serialized key bytes, then derive `localRowKey` from decoded key and Region only. The adapter, not the callback, adds Kafka partition to the canonical identity so partition-local ordering and compaction cannot collapse rows. Offset, timestamp, headers, partition, and other record metadata cannot influence decoding or the callback. Delete-only sources may additionally use the decoded non-null value and reject null-valued records instead of treating them as tombstones. Both declarations are mandatory because cleanup changes the public identity callback and retention changes row lifetime.

The aggregate Kafka Node Layer batches effective topic-configuration discovery per Region through `@platformatic/kafka` Admin before providing the Kafka Source Adapter Runtime Service. It normalizes `cleanup.policy` as an unordered whitespace-insensitive set, requires exact agreement with the declaration, and resolves `match-kafka-retention` from `retention.ms`. Failure is a typed Layer acquisition error and prevents the complete View Server Runtime Effect from starting. This deliberately creates a narrow exception to ordinary Source Supervision: running without a verified broker contract could silently corrupt the materialized view, and a health hook cannot make an invalid runtime safe. Validation is a point-in-time startup snapshot. V1 supports broker-policy changes only through coordinated stop, broker change, and restart of every affected instance; it deliberately does not poll, and mutation behind a running instance is outside the correctness contract.

Kafka Retention Projection uses the Kafka record timestamp and Region-resolved duration. A logical Materialized Topic lifetime owns a lightweight expiry index, keyed serialization, and one coarse Effect Clock sweep across Source Attempt retries. One Source Attempt Scope finalizer owns a live-lease registry. Before any Upsert or keyed Delete delivery—including tombstones and already-expired non-null authoritative records—`Effect.uninterruptibleMask` makes permit acquisition and insertion of its idempotent lease into that registry one interruption-safe ownership transfer, releasing on registration failure before restoring interruption. Ordinary release removes the registry entry, bounding retained finalizer state by concurrent live leases. Runtime Core requires every transition-bearing retention delivery to contain exactly one mutation, rejecting multi-mutation shapes in public types and defensive runtime validation. It applies that singleton Topic Row mutation and a closed nominal Source Application Transition in one serialized uninterruptible critical section. The transition comes only from the SDK-owned Source Application State Module; it contains no callback, Effect, requirement, Promise, I/O, or suspension. On successful mutation it replaces an Upsert deadline or removes every keyed Delete deadline, including tombstones and already-expired non-null records, and releases the lease; failed mutation leaves the prior generation unchanged, and the attempt registry is the fallback before transition. External settlement receives every complete application Exit exactly once afterward and cannot create a row/index gap.

The sweep launches new work only while the source is `Ready` or `Degraded`, preserving retained rows during retry and exhaustion. Each due item uses `Effect.acquireUseRelease`, or an equivalent fresh child `Effect.scoped` acquisition, for the same lease; while holding it immediately before application, the item rechecks both generation and Source Status. A stale candidate performs no row mutation, preserves the current newer generation, and removes only the obsolete due entry and its exact failed-work identity. A non-ready status performs no mutation and retains the same due entry and failed-work identity for the next active sweep. No permit is registered in the logical-lifetime sweep Scope. The SDK-owned Source Application State Module issues a closed Source Maintenance Operation bound to the exact keyed Delete and matching-generation removal transition. The Source Maintenance Interface accepts only that sealed operation, never an arbitrary Source Mutation, and applies it in the same serialized uninterruptible critical section. A failed Delete leaves the row and generation indexed for later retry. The logical Materialized Topic Scope owns and joins the sweep fiber: only Scope-close interruption is ordinary; any other sweep failure or premature completion outside the per-item maintenance Exit contract is a fatal invariant breach that closes the complete runtime.

A delivery Source Application Transition executor defect becomes that delivery's defective application Exit. Runtime Core passes it to Source Settlement exactly once, records settlement failure only as secondary diagnostics, and then re-fails the original defect so settlement cannot mask the fatal invariant breach; Kafka does not commit either non-success Exit. A Source Maintenance Operation executor defect instead becomes the defective maintenance application Exit and invokes no Source Settlement. Both invariant breaches fail the complete runtime and close the logical lifetime; the maintenance `acquireUseRelease` or child Scope releases its lease. Safe reconstruction requires an authoritative replay position or durable checkpoint. Kafka v1 provides no checkpoint, so `latest`, `committed`, and bounded start positions do not guarantee automatic recovery of prior rows; recovery tests use an authoritative start. Non-completion is excluded by the closed operations.

An already-expired non-null authoritative record never produces a transient Upsert. Because Kafka timestamps need not be monotonic, it instead emits the same singleton keyed Delete and closed transition, removing a row produced by an earlier offset if present. Tombstones always take the keyed Delete path, and invalid items never refresh retention. The aggregate Kafka Node Layer supplies a positive finite sweep interval, defaulting to 15 minutes.

The Topic-Bound Source Toolkit gains one deep transport-neutral Source Maintenance Interface. It accepts only SDK-issued closed Source Maintenance Operations, applies them through the ordinary Column Live View Engine mutation and Delta path, returns the complete application Exit to adapter-owned maintenance, and never routes failure into Source Supervision. It also reports active/recovered Adapter Maintenance Failure markers without Runtime Core inspecting Kafka metrics. Runtime Core keeps a logical-lifetime degradation ledger through every supervision phase: settled item rejection remains sticky, while maintenance failed work is a set keyed by canonical ID plus generation. Repeated failures of one item increment retry metrics without increasing backlog cardinality. A successful retry removes the exact identity with its row/index generation; a newer successful delivery atomically replaces or removes the generation and cancels its now-stale identity. Interruption, retry suspension, and exhaustion retain the identity while its due generation remains indexed; explicit stale-generation observation may cancel it. The marker clears when the set is empty. Operational `Starting`, retry, exhaustion, and stopping statuses and their derived Topic/aggregate health retain precedence. A later readiness transition selects `Degraded` when the ledger remains non-empty, while clearing the last maintenance reason during readiness returns to `Ready`. Kafka Source Adapter Metrics retain the latest exact safe maintenance failure for the logical lifetime, replacing it only with a newer failure, so a sub-cadence failure and recovery still becomes observable on the next bounded metrics publication. A failed expiration therefore remains retryable and globally visible during active operation without stopping ingestion, exposing Runtime Client, or leaking a Kafka branch into Runtime Core.

`match-kafka-retention` intentionally means configured time-based retention rather than an exact mirror of the physical Kafka log. Kafka removes segments rather than individual records, may remove them later than `retention.ms`, and may remove them for `retention.bytes`; View Server does not inspect broker segment state or emulate size-based retention. Compact-only sources and `retention.ms = -1` retain forever. A matched zero still uses the universal `record timestamp + duration` deadline, so it is immediately due only when the record timestamp is not later than the sweep's Effect Clock time; a future-dated record becomes due at its own timestamp. Explicit positive durations may be shorter or longer than Kafka retention, and Effect infinity explicitly retains forever; explicit zero and negative durations are invalid.
